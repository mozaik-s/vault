# Vault Module - Agent Instructions

## Project Context

**Vault** is a generic encrypted asset storage library that serves as the core foundation for the **Mozaik** project—a secure, encrypted photo-sharing platform for families.

This module is part of a two-project architecture:
- **Vault** (`/Users/milanbor/projects/vault`) - Generic encrypted asset storage library (THIS REPOSITORY)
- **Mozaik** (`/Users/milanbor/projects/mozaik`) - Photo-sharing application that uses Vault

## What is Mozaik?

Mozaik solves a critical problem: families want a safe, private way to share photos of their children with trusted family members. Unlike existing solutions (WhatsApp, iCloud, Google Photos), Mozaik provides:

- **End-to-end encryption**: Images encrypted on the client before upload
- **Zero-knowledge architecture**: Server cannot see photos, even if compromised
- **Fine-grained access control**: Users control exactly who sees what
- **Family-first design**: Built specifically for parents and families
- **Simplicity**: No cryptography knowledge required from users

## Vault's Role

Vault is a **pure Erlang OTP library built with Mix** that serves as the foundational encrypted storage system. Mozaik (Elixir/Phoenix) imports Vault as a dependency via `mix.exs` and calls Erlang modules directly. This provides:

### Core Features (Phase 1)
1. **Accounts** - User registration & authentication with secure password handling
2. **Assets** - Upload/download encrypted images with streaming support
3. **Permissions** - Grant/revoke access using cryptographic signatures (Ed25519)
4. **Crypto** - Cryptographic operations (AES-256 encryption, Ed25519 signatures, Curve25519 key exchange)
5. **Audit** - Complete access logging and compliance tracking

### Security Guarantees
- ✅ Client-side encryption: Images encrypted before leaving the browser
- ✅ Server-side storage: Only encrypted blobs stored (never plaintext)
- ✅ Cryptographic permissions: Access control via Ed25519 signatures
- ✅ Private key isolation: Keys never leave client
- ✅ Audit trail: Complete logging of all access

## Development Guidelines

### Security First
- All code must follow the documented security model
- Private keys must never be exposed or serialized
- All asset uploads must be encrypted before transmission
- All access must be logged in the audit trail
- No plaintext storage of sensitive data

### Code Quality
- Maintain clear separation between encryption/crypto logic and business logic
- Write comprehensive tests for cryptographic operations
- Document all assumptions about key management
- Follow Phoenix and Elixir best practices

### Before Implementing
1. Check the documentation in `/Users/milanbor/Documents/mozaik_notes/`
2. Understand the security model and threat assumptions
3. Review the current architecture decisions
4. Consider how changes affect Mozaik integration

## When Working on This Repository

**Do:**
- Keep changes aligned with the documented security model
- Reference the documentation directory for context
- Ensure all crypto operations follow libsodium best practices
- Maintain backward compatibility with Mozaik integration
- Add/update tests for security-critical code

**Don't:**
- Implement undocumented security changes without team review
- Store plaintext sensitive data
- Bypass the documented permission system
- Make assumptions about key storage or handling
